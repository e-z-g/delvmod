
**Mounting evidence seems  to indicate that in some cases the position of things within a table is significant, an unfortunate development.** 

A `table` is a toplevel entity that implements an associative array, as distinct from a regular [array](Array). A table is indicated by the high nibble `A`, and the number of entries in the table immediately follows. E.g. a table with 11 elements would begin `A0 0B`. The entries follow immediately. Each entry consists of a four-byte value followed by a two-byte key. The entry must either be a `dref` or the atom `None` (`<5000FFFF>`), the latter being equivalent to not having any entry at all from the point of view of retrieving the value. (`index` will return `None` either way.) 

It is not possible for the table values to directly be other sorts of atomic values, e.g. integers or booleans; putting them as table values causes the script to crash. Rather, use a `dref` (i.e. `0x80000000|(resid<<16)|offset`). The interpreter will be in single-direct mode (i.e. direct mode, but it will only look for one entity; a nonstring character such as 00 terminates a string) when it reaches the address pointed to by the `dref`. Null-terminated strings can thus be pointed to directly, but if you want to store an integer you need to wrap it in an array (e.g `90 01 00 00 00 03`, = [3]). This is in fact the reason why scalar class variables like the weight of an object are nonetheless wrapped in arrays. An empty string would be returned if a bare `00 00 00 03` e.g. were at the offset, because the first `00` would be interpreted as a null termination. Likewise a boolean e.g. `true`/`<50000001>` would be returned as the string `"P"` because of the same misinterpretation. 

One might think that the opcode `class_variable x y` i.e. `61xxyy` would work for any table, but it seems to only work with tables that are the dispatch table of objects. Use `index` (`46`) instead to retrieve fields, and suck it up and use it twice to retrieve the integer from inside a wrapping array as described above. 

Table keys retrieved with `index` can be up to 0x7FFF. This is not a matter of signedness convention (i.e. the table keys are all interpreted as unsigned integers but load_short loads a signed integer - it was verified using load_word). However, many classes, without apparent rhyme or reason, contain `None`-valued entries with keys in violation of this rule. Their significance is extremely obscure.  Sometimes semantically related objects (e.g. farming implements) contain similar keys. One hypothesis is that these `None` entries are as dead as the indistinguishably of a `None` entry from no entry at all using `field` implies, and that they were propagated by copying and pasting (hence why e.g. all farm implements would share some dead values.)
